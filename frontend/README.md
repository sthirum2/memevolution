# Memevolution — frontend

An AI that writes memes, posts them, watches what really happens, and changes its strategy
based on the results. This repo is the **frontend only**: the screens that make that loop
easy to understand in about a minute.

Built for HopHacks 2026, Calcifer Computing memetics track.

It runs on saved demo data out of the box. The backend swaps in behind one env flag with no
component changes — see [Backend integration](#backend-integration).

---

## Run it

```bash
npm install && npm run dev
```

Open http://localhost:5173. No `.env` needed — demo data is the default.

| Script               | What it does                                               |
| -------------------- | ---------------------------------------------------------- |
| `npm run dev`        | Dev server on :5173                                         |
| `npm run build`      | Type-check then production build to `dist/`                 |
| `npm run preview`    | Serve the production build                                  |
| `npm run format`     | Prettier over `src/`                                        |
| `npm run mock:regen` | Regenerate the demo data and specimen images                |

## The three screens

**1. The memes** — every meme the AI has ever made, laid out round by round. A single strip at
the top shows the whole family tree at a glance (no zooming or panning); clicking a round
shows its memes as cards. The winner of each round is outlined in green and becomes the
parent of the next. **Play the whole story** walks through all six rounds on its own — this is
the one-click demo. Clicking any meme opens the full story behind it: what the AI changed,
why it thought that would work, what it predicted, and what actually happened.

**2. Try it** — run a round yourself in four steps. Pick a platform and topic, watch the AI
write five memes and score them, review the one it picked, approve it, then watch the results
come in and feed back into the AI.

**3. What it learned** — the proof. A before-and-after of every opinion the AI holds, a chart
of how those opinions moved round by round, and a scatter of predicted-versus-actual showing
whether it is genuinely getting better at guessing.

### Design rules

- **Scores are 0–100**, never decimals. `73` reads instantly; `.73` does not.
- **Plain English everywhere.** The data contract keeps machine names like `absurdity` and
  `trend_relevance`; the UI shows "Weirdness" and "On-trend". The mapping lives in one file,
  [`src/lib/plain.ts`](src/lib/plain.ts).
- **Colour means one thing only:** green spread, red flopped, blue is a prediction rather
  than a result, purple is the AI itself. All defined in `tailwind.config.js`.
- **Nothing needs a legend to read.** If a number needs explaining, the explanation sits next
  to it.

### Demo data

Generated by `scripts/generate-mock.mjs` — the storyline is hand-written, the numbers are
computed. Six rounds, 21 memes, including two deliberate surprises: one meme beat its
prediction by 18 points, and the AI's push into irony missed by 33 points, which is what
taught it that the historical data had misled it. Edit the `SPEC` table in the script and run
`npm run mock:regen`.

Preview images are local SVGs in `public/specimens/` — no network calls during a demo, so bad
venue wifi can't break the presentation.

## The frozen data contract

Defined in [`src/types/index.ts`](src/types/index.ts). All four roles agreed this shape; don't
add or rename fields without telling the team.

```ts
Experiment {
  id: string                 // "exp_006"
  generation: number
  parent_id: string | null
  status: 'pending' | 'predicted' | 'deployed' | 'survived' | 'extinct'
  genome: {
    topic, humor, format, hook, audio_strategy: string
    absurdity, irony, relatability, trend_relevance, text_density: number  // 0..1
    caption_length, video_length: number                                   // counts
  }
  mutations: { trait: string; from: number | string; to: number | string }[]
  hypothesis: string
  prediction: {
    fitness: number          // 0..1 — the UI shows it as 0–100
    confidence: number
    feature_attribution: { feature: string; contribution: number }[]
  }
  content: { headline, visual_description, punchline, caption, audio, media_url: string }
  deployment: { platform: 'tiktok'|'instagram'|'x'|null; timestamp: string|null; post_id: string|null }
  observed: {
    views, likes, comments, shares, saves, fitness: number | null
    timeseries: { t: string; views: number; likes: number; shares: number }[]
  }
}

AgentState {
  generation: number
  beliefs: Record<string, number>      // 0..1 per trait
  confidence: Record<string, number>
  note: string
}
```

| Role | Owns |
| --- | --- |
| data-model | `prediction` |
| agent | `genome`, `mutations`, `hypothesis`, `content` |
| frontend | displays it, writes nothing |
| backend | persists it, fills `deployment` and `observed`, serves `AgentState` |

The belief keys the charts plot are `absurdity`, `irony`, `relatability`, `trend_relevance`,
`text_density`, `short_video`, `trending_audio`, `short_caption` (`BELIEF_TRAITS` in
`src/lib/fitness.ts`). New keys won't crash anything, but they won't be plotted until they're
added to that array and given a plain-English name in `src/lib/plain.ts`.

## Backend integration

**This is the whole handover. Nothing in the component tree needs to change.**

### 1. Implement the endpoints

`src/api/http.ts` is already written against these.

| Client function | Method & path | Request body | Response |
| --- | --- | --- | --- |
| `getExperiments()` | `GET /experiments` | — | `Experiment[]` |
| `getExperiment(id)` | `GET /experiments/{id}` | — | `Experiment \| null` |
| `getAgentStates()` | `GET /agent-states` | — | `AgentState[]` |
| `getGenerations()` | `GET /generations` | — | `GenerationSummary[]` |
| `getCorpus()` | `GET /corpus` | — | `CorpusStats` |
| `generateCandidates(params, onCandidate?)` | `POST /generation` | `{ platform, topic, riskAppetite, count }` | `Experiment[]` (5 scored candidates) |
| `selectCandidate(candidates, riskAppetite?)` | `POST /select` | `{ candidate_ids: string[], risk_appetite: number }` | `SelectionResult` |
| `commitCandidate(candidate)` | `POST /experiments` | `Experiment` | `Experiment` with a server-assigned `id` |
| `deployExperiment(id, platform)` | `POST /experiments/{id}/deploy` | `{ platform }` | `Experiment`, status `deployed` |
| `recordMetrics(id, metrics)` | `POST /experiments/{id}/metrics` | `{ views, likes, comments, shares, saves }` | `Experiment` with `observed.fitness` filled |
| `evolve()` | `POST /evolve` | — | `EvolveResult` |

Supporting shapes (all in `src/types/index.ts`):

```ts
GenerationSummary { generation, count, meanFitness, bestId, bestFitness }
SelectionResult   { selectedId, mode: 'exploit'|'explore', reasoning, ranking: {id,fitness,confidence}[] }
EvolveResult      { generation, previous: AgentState, next: AgentState,
                    shifts: {trait,from,to,delta}[], driverId: string|null }
CorpusStats       { datasets[], fitnessDistribution[], traitCorrelation[], propagationByFormat[] }
```

Notes:

- **`POST /generation` returns all five candidates at once.** The Try-it screen reveals them
  one at a time for effect; `http.ts` replays the batch through the same callback so the UI
  behaves identically. If you add SSE later, change the body of `generateCandidates` in
  `http.ts` — the signature and every caller stay as they are.
- `commitCandidate` exists because a generated candidate needs a real server-side id before it
  can be deployed. If `POST /generation` already persists candidates, make it return its
  argument unchanged.
- `recordMetrics` should compute `observed.fitness` server-side. The frontend never calculates
  fitness, it only displays it. The demo's definition is propagation-weighted and normalised
  for reach — see `recordMetrics` in `src/api/mock.ts` for the weights we've been demoing.
- `SelectionResult.reasoning` is shown to the user, so write it for a general reader.
- Timestamps are ISO 8601. `observed.timeseries` may be empty.
- Enable CORS for `http://localhost:5173`.

### 2. Flip the flag

```bash
# .env
VITE_USE_MOCK=false
VITE_API_BASE_URL=http://localhost:8000
```

Restart the dev server. The chip in the header flips from "Demo data" to "Live", so it's never
ambiguous which backend answered.

### 3. That's it

No component imports JSON and no component calls `fetch`. `src/api/client.ts` picks the
implementation from that one flag. If a request fails, the app shows the error and a retry
button rather than a blank screen.

To check the swap worked: load the app, confirm the header says "Live", open **The memes**
(proves the two GETs), open **What it learned** (proves `GET /agent-states`), then run one
round in **Try it** (proves the four POSTs).

## Honest caveats

Worth keeping in the pitch, since judging is on the memetics argument:

- **"Spread score" is our own measure**, not a measure of going viral. It weighs shares and
  saves heavily and adjusts for audience size, so a small account that gets passed around
  beats a big one that just gets seen. Hovering any headline score shows the exact breakdown,
  and `scripts/generate-mock.mjs` fails the build if the demo data's scores stop matching
  their own engagement numbers.
- **Traits like "weirdness" are AI judgements**, not facts about the world.
- **The chance-of-spreading percentage is a defined quantity** — the modelled probability of
  beating the top 10% of the historical data — and the app shows the AI being wrong about it.
- **Nothing posts automatically.** The AI picks; a person ticks the box and presses the button.
